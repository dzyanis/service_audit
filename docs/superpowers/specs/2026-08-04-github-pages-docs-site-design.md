# Design: open web version on GitHub Pages

Date: 2026-08-04
Status: approved for planning

## Goal

Publish the assessment as a browsable, searchable, Google-indexable website at
`https://dzyanis.github.io/service_audit/`, built from the Markdown already in the
repository.

Today the content is readable only as Markdown on github.com or as a raw file.
GitHub's blob views are indexed poorly and read badly on a phone, so the
framework is effectively invisible to anyone who has not already been sent the
repository link.

## Non-goals

- No interactive scoring tool. The site is content, not an application.
- No redesign of the assessment content. Wording, item IDs, and file layout are
  unchanged.
- No custom domain for now. `site_url` is set in one place so a later move is a
  one-line change plus a `CNAME` file.

## Hard constraint: the Markdown files are an API

`AGENT.md`, `scripts/build-bundle.sh`, and anyone running the documented
`curl` command all consume the Markdown files directly. The site build must
therefore not modify any tracked `.md` file: no YAML front matter, no renames,
no restructuring. This is what rules out Jekyll themes, which require front
matter in every page for titles and nav ordering.

MkDocs Material keeps nav and titles in `mkdocs.yml`, leaving content files
untouched. That is the deciding reason for the choice.

## Architecture

A build script stages content into a gitignored directory, then runs MkDocs
against that staging directory. Nothing tracked is mutated.

```
repo root ──stage──> .site-src/ ──mkdocs build──> site/ ──deploy──> GitHub Pages
```

### Staging

`scripts/build-site.sh` copies the published files into `.site-src/`,
**preserving relative paths**. Path preservation is what makes the existing
relative links work with no rewriting: MkDocs resolves a `.md` link target to
that page's URL automatically, so `assessment/01-product-vision.md` and
`../ASSESSMENT.md` both keep pointing at the right page.

Staged files:

| Source | Staged as |
|---|---|
| `README.md` | `index.md` |
| `ASSESSMENT.md` | `ASSESSMENT.md` |
| `assessment/*.md` (7 files) | same path |
| `coverage/*.md` (6 files, incl. `README.md`) | same path |
| `templates/report.md` | same path |
| `AGENT.md`, `CONTRIBUTING.md`, `CHANGELOG.md` | same path |
| `site-assets/robots.txt` | `robots.txt` |

Deliberately **not** staged:

- `service-audit-full.md`. It is a generated 90KB duplicate of every category
  page. Publishing it would put the same text on two indexable URLs and split
  their ranking signal. It remains in the repository and at its raw URL, which
  is how the documented web-chat workflow already consumes it.
- `LICENSE` (not Markdown), `scripts/`, `.github/`, `docs/`.

### Link rewrites

Renaming `README.md` to `index.md` and dropping the bundle breaks four links.
The staging script applies exactly these rewrites to the staged copies, and
nothing else:

| In | From | To |
|---|---|---|
| `index.md` | `](service-audit-full.md)` | `](https://raw.githubusercontent.com/dzyanis/service_audit/main/service-audit-full.md)` |
| `index.md` | `](assessment/)` | `](ASSESSMENT.md)` |
| `index.md` | `](coverage/)` | `](coverage/README.md)` |

All three are in `index.md`. Every other internal link in the repository
already resolves unchanged, including `](README.md)` in
`coverage/agile-manifesto.md`, which points at a real staged file.

The two directory-style links (`assessment/`, `coverage/`) render as directory
listings on github.com but have no equivalent on a static site. `assessment/`
points to `ASSESSMENT.md`, which lists all seven category files with links.
`coverage/` points at the real index page for that section.

The rewrite list lives in one clearly commented block in the script. Anything
missed is caught by the build, not shipped (see Testing).

### Heading anchors must stay GitHub-compatible

Six existing cross-references use anchors generated by GitHub's slug
algorithm, for example:

```
04-code-quality.md#414-dependency-security--updates
```

Note the double dash, which is what GitHub produces when it strips the `&`
from "Security & Updates" and leaves two spaces behind. Python-Markdown's
default slugifier collapses that to a single dash and would silently break all
six links.

`mkdocs.yml` therefore configures the GitHub-compatible slugifier:

```yaml
markdown_extensions:
  - toc:
      permalink: true
      slugify: !!python/object/apply:pymdownx.slugs.slugify {kwds: {case: lower}}
```

The `case: lower` argument is required: without it the slugifier preserves the
original capitalisation and the anchors stop matching GitHub's.

This also keeps every item-level anchor (`#11-product-overview`) identical
between github.com and the website, so links shared from either source resolve
in both.

### Navigation

Nav is declared in `mkdocs.yml`:

- Home (`index.md`)
- The Assessment (`ASSESSMENT.md`)
  - the seven category pages, in numeric order
- Framework coverage (`coverage/README.md`)
  - the five mapping pages
- Running it with an agent (`AGENT.md`)
- Report template (`templates/report.md`)
- Contributing (`CONTRIBUTING.md`)
- Changelog (`CHANGELOG.md`)

Page titles come from each file's existing H1. No file needs a title override.

## Search engine indexing

The site is crawlable because of the following, all of which are configuration
rather than content work:

- **Pre-rendered static HTML.** Every word is in the served markup. Nothing
  depends on client-side rendering, so indexing does not wait on Google's
  render queue.
- **`site_url`** set to `https://dzyanis.github.io/service_audit/`. MkDocs uses it
  to emit `sitemap.xml` automatically, and Material emits a
  `<link rel="canonical">` on every page. The canonical tag matters here
  specifically: it tells Google to prefer these pages over the github.com blob
  views of the same Markdown.
- **`robots.txt`** at the site root, allowing all crawlers and declaring the
  sitemap location.
- **`site_description`**, used as the meta description.
- **Per-page `<title>`** derived from the H1, rendered as
  `Page title - Software Project Maturity Assessment`.
- **Stable per-item anchors**, so individual assessment items are linkable and
  can surface as jump-to-section results.

Material's built-in search is a reader convenience and carries no SEO weight.

Two steps are manual and must be done by the repository owner:

1. Settings > Pages > Source set to "GitHub Actions". The workflow cannot
   enable this itself.
2. Verify the property in Google Search Console and submit the sitemap.
   Indexing then takes days to weeks, not hours.

## Deployment

`.github/workflows/site.yml`:

- On push to `main` affecting content: build and deploy via
  `actions/upload-pages-artifact` and `actions/deploy-pages`.
- On pull request: build only, no deploy.
- Python dependencies pinned in `requirements-docs.txt`
  (`mkdocs-material` and its transitive pins) so a Material release cannot
  break a deploy unannounced.

## Testing

The build is the test. `mkdocs build --strict` promotes every warning to a
build failure, which covers:

- links to files that do not exist, including anything the rewrite table
  missed;
- broken heading anchors, via `validation.links.anchors: warn` in
  `mkdocs.yml`, which catches a regression in the slugifier configuration.

Because the same build runs on pull requests, a broken link fails review rather
than reaching the published site.

Additionally, the workflow runs `git diff --exit-code` after the build to prove
no tracked file was modified, enforcing the hard constraint above. This check
lives in CI rather than in `build-site.sh`, so that running the script locally
with unrelated work in progress does not fail.
